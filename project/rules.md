# Project Rules

These rules are mandatory for implementation agents and reviewers.

## 1. Product behavior comes from specifications

Do not invent features or expand scope because an idea seems useful.

If a product behavior is missing and materially affects implementation, record it in `project/open-decisions.md` and ask the owner at the phase where it becomes blocking.

## 2. One user owns one private personal space

Multiple accounts are supported.

Each account owns its dashboards and associated data.

Do not build:

- organizations;
- workspaces;
- teams;
- shared dashboards;
- per-dashboard collaboration;
- role/permission matrices between normal users.

## 3. Dashboards are data, not hard-coded sections

`Home`, `Travel`, and `Dev` are names/examples, not separate application architectures.

The user can create dashboard tabs and assemble any allowed widget on them.

Travel-specific and Dev-specific widgets may be catalogued by category, but they still use the same dashboard engine.

## 4. Widget behavior is explicit

Every widget type must define:

- stable type identifier;
- configuration schema;
- allowed sizes;
- default size;
- rendering behavior for each supported size family;
- loading/empty/error behavior;
- whether it needs a provider/server boundary;
- whether it stores normalized data or instance JSON only.

A widget must not accept arbitrary dimensions.

## 5. Grid behavior

Desktop/tablet landscape uses 8 logical columns.

Vertical rows are unbounded.

Global widget height maximum is 3 rows.

Device layouts are independent.

A resize may only resolve to a size declared legal by that widget type.

## 6. Normal mode vs edit mode

Normal mode:

- widgets are stable;
- no accidental dragging/resizing;
- operational widget controls remain usable.

Edit mode:

- add;
- move;
- resize;
- configure;
- duplicate;
- remove.

## 7. Persistence

PocketBase is the persistent backend and authentication source.

Do not persist passwords generated by the Password Generator.

Do not treat transient external market/weather/calendar results as business records unless a later spec explicitly requires historical persistence.

## 8. Security

Never expose:

- PocketBase superuser credentials;
- Google OAuth client secrets where a secret is applicable;
- AI provider API keys;
- encryption keys;
- server-only integration tokens.

External provider secrets must not be readable by normal browser-side PocketBase requests.

## 9. External integrations

External providers must be isolated behind explicit interfaces/adapters.

Widgets must consume normalized app-level responses rather than provider-specific raw payloads.

One integration failure must not make the entire dashboard fail.

## 10. Data ownership

Every normal user-owned collection must enforce owner filtering with PocketBase access rules and app-layer checks where relevant.

Never rely solely on hiding UI controls for authorization.

## 11. Styling

The product is terminal/TUI-inspired, not a literal terminal emulator.

Use:

- mostly monospaced typography;
- high information density;
- dark-first design;
- thin borders;
- restrained color;
- minimal shadow;
- compact controls;
- functional motion only.

Avoid generic SaaS card aesthetics, oversized marketing typography, glassmorphism, heavy gradients, and decorative dashboards.

## 12. Dependencies

Do not add a major UI framework, state-management system, grid framework, or provider SDK solely for convenience without explaining why the native/smaller approach is insufficient.

The accepted core stack must not be replaced without owner approval.

## 13. SDD workflow

Use OpenSpec files for substantial changes.

Do not maintain duplicate SDD artifacts elsewhere.

The phase brief is input. OpenSpec proposal/spec/design/tasks are the implementation contract.

## 14. Commits

Prefer small, coherent commits aligned with SDD tasks.

Do not mix unrelated cleanup/refactors into feature work.

## 15. Documentation truth

Do not mark planned work as implemented.

`project/context.md` describes verified current state only.
