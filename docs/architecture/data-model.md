# PocketBase Data Model — Target MVP

This document describes the intended MVP data model and the Phase 0002 records that are already implemented. Exact PocketBase migration syntax belongs to the relevant SDD design/apply phase and migration files.

## Ownership principle

All normal user data is private to one authenticated user.

Every user-owned record must carry an `owner` relation to the auth collection unless ownership is safely implied by a relation whose rules enforce the same boundary.

Prefer explicit owner fields for simpler rules and debugging.

Phase 0002 verifies owner-scoped PocketBase rules with normal user tokens for profiles, preferences, dashboards, and dashboard widgets.

## `users` — auth collection

PocketBase auth collection.

Phase 0002 extends it with:

- `displayName`
- `avatarKey`
- `timezone`
- `onboardingCompleted`
- `onboardingCompletedAt`

`onboardingCompletedAt` is server/hook-owned. Normal users cannot directly mark onboarding complete without satisfying the hook predicate.

Avoid storing arbitrary uploaded avatar files in MVP. `avatarKey` references bundled 8-bit assets.

Public self-registration is not implemented in Phase 0002. Users are provisioned administratively before login.

## `user_preferences`

One record per user.

Implemented Phase 0002 fields:

- `owner` relation -> users, unique
- `appearance`: `dark | light | system`
- `defaultLocation` JSON containing the onboarding/default location payload or `null`

Do not turn this into an unstructured dumping ground.

## `dashboards`

Implemented Phase 0002 fields:

- `owner` relation -> users
- `name`
- `sortOrder`
- `seedKey`
- `created`
- `updated`

A dashboard belongs to exactly one user.

Phase 0002 seeds exactly one initial dashboard for a completed user:

- `name: "Home"`
- `sortOrder: 0`
- `seedKey: "home"`

The migration adds a unique index for non-empty `(owner, seedKey)` values so the seeded Home dashboard is idempotent per owner.

Optional fields such as slug/icon should only be added if a future UX/spec requires them.

## `dashboard_widgets`

Implemented Phase 0002 fields:

- `owner` relation -> users
- `dashboard` relation -> dashboards
- `type` stable string identifier
- `seedKey`
- `config` JSON
- `layoutDesktop` JSON
- `layoutTablet` JSON
- `layoutMobile` JSON
- `created`
- `updated`

Phase 0002 seeds exactly four widget records on the Home dashboard:

- Search: `type: "search"`, `seedKey: "search"`
- Local Clock: `type: "clock"`, `seedKey: "clock"`
- Local Weather: `type: "weather"`, `seedKey: "weather"`
- Bookmarks: `type: "bookmarks"`, `seedKey: "bookmarks"`

Each seeded widget belongs to the same owner as the Home dashboard. The migration adds a unique index for non-empty `(dashboard, seedKey)` values so widget seeding is idempotent per dashboard.

Initial Phase 0002 widget layouts are `null` for desktop, tablet, and mobile. Widgets are persisted as seed data but are not rendered as functional dashboard widgets until later dashboard/widget phases.

### Layout payload

A future device layout should contain only the information necessary to validate/place the widget, typically:

```json
{
  "x": 0,
  "y": 0,
  "w": 2,
  "h": 1
}
```

The widget registry remains authoritative for whether `w/h` is legal for that type.

Do not trust stored layout JSON without validation.

### Config payload

Instance-specific widget configuration lives here when it has no independent lifecycle/query value.

Phase 0002 seed configs are generated by the onboarding validation boundary:

- Search and Bookmarks use initial empty/built-in config.
- Local Clock stores local clock mode and the selected timezone.
- Local Weather stores the selected default location or `null`.

Do not store normalized bookmark or secret records inside this JSON.

## Onboarding and minimal Home invariants

The verified Phase 0002 flow is:

```text
administratively provisioned user
→ login
→ session refresh/projection
→ onboarding when incomplete
→ idempotent Home seed on completion
→ minimal protected Home when completed
```

Onboarding completion creates or validates preferences, the Home dashboard, and the four seeded widgets before finalizing the profile through a normal-user PocketBase batch.

Seed conflicts or inconsistent seed state are surfaced as safe conflict/unavailable API responses. The Home GET route validates the existing Home seed and returns only `{ dashboard: { id, name: "Home" }, initialized: true }`; it does not create, repair, or expose widget records.

Home/session responses are private and no-store.

## `bookmark_categories`

Fields planned for later phases:

- `owner`
- `name`
- `sortOrder`

Category is optional from a bookmark's perspective.

## `bookmarks`

Fields planned for later phases:

- `owner`
- `category` optional relation -> bookmark_categories
- `name`
- `url`
- `sortOrder`

Do not store a manually uploaded icon in MVP.

Favicon is derived at presentation/runtime level from the URL with a deterministic fallback.

## `search_engines`

User-configurable external search aliases planned for later phases.

Suggested fields:

- `owner`
- `name`
- `alias`
- `urlTemplate`
- `sortOrder`
- `enabled`

Google is the default behavior. It may be seeded as a record or represented as a built-in default; the relevant later phase design must choose one consistent approach.

`urlTemplate` must have a safe, documented query placeholder contract.

## `scratchpad_entries`

Purpose: lightweight scratchpad content/history only.

Suggested fields:

- `owner`
- `widget` relation -> dashboard_widgets
- `content`
- `archivedAt` nullable
- `created`
- `updated`

Invariant: one active (`archivedAt = null`) entry per Scratchpad widget instance.

The app must preserve this narrow scope and not evolve it into a general notes model during MVP work.

## `market_watchlist_items`

Central user list managed in Settings > Markets.

Suggested fields:

- `owner`
- `symbol`
- `displayName` optional
- `sortOrder`
- `enabled`

Markets widget configuration may reference/select watchlist items or use the user's current tracked list, depending on the Phase 0006 design. Multiple symbols in one widget is required.

## Calendar preference records

Use explicit collections/fields for:

- user's Google connection metadata;
- selected external calendar IDs;
- display preferences if needed.

Sensitive OAuth credentials/tokens must be server-only and not readable via normal user API rules.

The exact token storage strategy is resolved in Phase 0007.

## AI credential/settings records

AI settings require:

- owner;
- provider;
- model;
- optional endpoint/base URL if the selected provider design supports it;
- encrypted credential material.

Credential records MUST NOT be readable from browser-side PocketBase API calls.

Encryption keys MUST live outside PocketBase and source control.

## Data intentionally not persisted by default

Do not create historical collections for these unless a later spec requires them:

- weather observations;
- stock prices;
- exchange rates;
- Google Calendar event copies;
- generated passwords;
- AI translation history.

Transient caching may be introduced as an implementation concern when justified, but it is not user-domain history.

## Access rule intent

For normal owner collections, list/view/create/update/delete rules must ensure authenticated owner isolation.

Never rely on the frontend to filter another user's records after retrieval.

Server-only sensitive collections should deny normal client access and be reachable only through trusted server operations.
